# BILLING_TOKEN_RECOVERY_KEY — operational runbook

Honest scope: this deployment has **no KMS, HSM or Vault**. The recovery key is a
server-side environment secret. It is not readable by the browser, by database
clients, or from SQL, and it does not live beside the ciphertext (which lives in
Postgres) — but it is **not hardware-backed key management**.

## 1. Generation

- 64 characters of random material, e.g. `openssl rand -hex 32`.
- Never generated by hand, never derived from a password, never reused across
  environments.
- Stored as `BILLING_TOKEN_RECOVERY_KEY_V<n>` in the project's server secrets.

## 2. Storage and access control

| Aspect | Reality |
| --- | --- |
| Location | Project server secret store (injected into the server runtime only) |
| Readable by | Server handlers via `process.env` |
| Not readable by | Browser bundle, database, SQL, logs, clients |
| Backup | The value must also exist in the product owner's password manager. There is no other copy. |
| Rotation trigger | Suspected exposure, personnel change, or annual hygiene |

## 3. Loss

If the secret is lost and no backup exists:

- Outstanding encrypted envelopes become permanently unopenable.
- Entitlements are unaffected (they never depend on the envelope).
- Affected rows park in `recovery_required` and must be acknowledged manually
  through the Play Console before their 3-day refund window closes.
- Recovery: set a new key version and continue; historical envelopes are lost.

This is the single highest operational risk in the billing subsystem.

## 4. Rotation (non-destructive, supported)

Rotation is **additive**. Decryption reads the key version recorded inside each
envelope, so old envelopes keep opening while their secret remains configured.

1. Generate `BILLING_TOKEN_RECOVERY_KEY_V<n+1>`. Do not touch `V<n>`.
2. Deploy with **both** versions present and
   `BILLING_TOKEN_RECOVERY_KEY_VERSION=<n+1>`. New envelopes seal with the new
   key; existing ones still open.
3. Wait at least **7 days** (the recovery retention window) and confirm no
   `billing_ack_state` row still carries `recovery_key_version = <n>`.
4. Only then remove `BILLING_TOKEN_RECOVERY_KEY_V<n>`. This is the only
   destructive step.

Encoded in `src/lib/release/recovery-key.ts` (`rotationPlan`, `rotationIsSafe`)
and asserted by `PHASE13-T5`.

Never: rotate by overwriting `V1` in place. That instantly destroys access to
every outstanding envelope.

## 5. Reconciliation scheduler configuration

The recovery worker only runs when something calls
`POST /api/public/billing/reconcile`.

| Setting | Value |
| --- | --- |
| Method | `POST` |
| URL | `https://together-rooms.lovable.app/api/public/billing/reconcile` |
| Auth | header `x-reconcile-secret: <BILLING_RECONCILE_SECRET>` |
| Interval | every 15 minutes (allowed range 5–360) |
| Timeout | 60s |
| Retry | on `503`/timeout, retry with backoff; work is idempotent |
| Disabled state | Without `BILLING_RECONCILE_SECRET` the route returns 404 — fails closed |

Rules enforced in `src/lib/release/scheduler.ts` (`PHASE13-T3`):
secret ≥ 32 chars, https only, secret **never** in the URL, interval ≤ 6 hours
(the retry ladder caps at 6h and Play refunds at 3 days).

**Required external setup (not configurable from this project):** a cron
service (Google Cloud Scheduler, GitHub Actions schedule, cron-job.org, or an
equivalent) that issues the POST above with the header. Monitoring: alert if no
successful `200` response is observed within 60 minutes, and alert on any
`billing.ack.recovery_required` or `billing.ack.terminal_failure` metric.
